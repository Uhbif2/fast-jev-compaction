## 2. Главные выводы

**2.1. Автокомпакция через `turn.complete` не работает.**
Все 11 уникальных границ компакции с 20.09 (`compact_boundary` в транскриптах) запущены вручную
(`manual`), ни одной `plugin` или `auto`, хотя сессии доходили до 540–680k токенов при пороге 20–30%.
В бандле 2.1.275 есть текст ошибки: `$.session.compact: a turn is running …; the conversation
compacts between turns, so call it from turn.complete or later`. Хук же вызывал его внутри
`turn.complete` до `next(event)`, то есть до того, как ядро закрыло ход. Ошибка уходила только в
`ui.log`. Дефект унаследован от upstream.
*Поправка (вторая часть того же дня):* в первой версии разбора здесь утверждалось, что такой
вызов обходит собственный Jev-хук и уходит в саммари Claude. Это неверно: движок пропускает
только вызывающий хук («the calling hook alone is skipped», «the plugin's others see it»), так
что `session.compact` того же плагина событие получает.

**2.2. Компакция падает на длинных сессиях, то есть именно тогда, когда нужна.** Синтетический
бенчмарк, фиктивный Jev отвечает мгновенно, профиль владельца:

| Сессия | Результат |
|---|---|
| en, 60 пар инструментов, 163 сообщения | 1 запрос, 0.2 с |
| ru, та же | 2 запроса, 1.7 с |
| en, 150 пар, 406 сообщений | 4 запроса, **9.6 с чистого CPU на планирование** |
| ru, 150 пар | **FAIL**: `internal shard planner exceeded Jev state limit (~30863, limit 30861)` |
| en, 300 пар | **FAIL**: та же ошибка |
| ru, 300 пар, 23k символов пользовательского текста | **FAIL**: `all user messages plus the minimal global dialogue index exceed…` |

Три причины. Две из них — баги, см. §3. Третья — оценщик токенов считает каждый кириллический
символ отдельным токеном по 0.9: 1000 символов русского = 766 «токенов», английского = 214 (3.6×).
Реальные токенизаторы дают для русского примерно 250–400 на 1000 символов. Инвариант «все
сообщения пользователя дословно в каждом шарде» упирается в жёсткий потолок: около 23k символов
русского текста пользователя на всю сессию. Дальше компакция невозможна совсем.

**2.3. Экономика кэша против `minReductionRatio=0`.** Применённая компакция переписывает
prompt-кэш от первого изменённого сообщения, то есть почти весь контекст. Сессии Code используют
часовой кэш: запись 2×, чтение 0.1×. Для контекста 300k: сокращение на 5% окупается примерно за
360 ходов, на 50% — примерно за 18. Мелкие компакции в токенах убыточны, а порог 0 применяет
любые. Цель — не максимальное сокращение за проход, а редкие и глубокие проходы. Порог в
процентах окна сам по себе такой цели не задаёт. (Расчёт по ценам API; для подписки пропорции,
вероятно, похожи, но это не проверено.)

**2.4. Семантика «ничего не делать» неверна.** В no-op, при малом сокращении и при ошибке хук
возвращает исходный список сообщений ([hooks/fast-jev.ts:394](../hooks/fast-jev.ts:394), 420,
432, 455). Для движка это состоявшаяся компакция: он пишет boundary и заново подкладывает контекст.
Пример — no-op 21.09 длился 17 мс, а `postTokens` вырос с 2518 до 61802. У движка есть `{ skip: reason }`:
«the conversation stays as it is and one line says why».

## 3. Подтверждённые баги (воспроизводятся)

1. **Метка шарда при планировании короче финальной.** Планировщик проверяет, помещается ли
   группа, по состоянию с `shard: 'planning'` (4 токена по оценщику) —
   [src/state.ts:513](../src/state.ts:513). Финальное состояние собирается с меткой
   `'N/M: historical assistant slice'` (до 11 токенов) — [src/state.ts:568](../src/state.ts:568).
   Если жадно заполненный шард оказался в пределах ~7 токенов от лимита, он превышает лимит.
   Тогда бросается исключение, и компакция целиком падает. Воспроизведение — §2.2, строки FAIL
   `internal shard planner`.
2. **Мнимый fallback для одного большого сообщения assistant.** Проверка «влезет ли одно
   сообщение» идёт с минимальной сборкой (без индексов и якоря) —
   [src/state.ts:534](../src/state.ts:534). Финальный шард собирается с обычной сборкой. В полосе
   между ними всегда падает `internal shard planner exceeded`. Воспроизведение: 40 коротких
   сообщений assistant, одно на `'word '.repeat(2350)`, лимит 4170–4300 → FAIL, от 4500 → ok.
3. **Ложное «тесты подтверждают отказ» в имени теста.** [tests/hook.test.ts:143](../tests/hook.test.ts:143)
   называется «…so the hook falls back», а fallback отключён. Мелочь, но вводит в заблуждение.

## 4. Слабые места по слоям

### Надёжность
- **Нет общего дедлайна.** До 10 попыток с паузами 1+2+4+8+15+30×4 = 150 с на один батч
  ([hooks/fast-jev.ts:50](../hooks/fast-jev.ts:50)). Таймаута запроса нет (у `HttpInit` его и
  нет — нужен `Promise.race`). `Retry-After` игнорируется: адаптер выбрасывает `headers`
  ([hooks/fast-jev.ts:38](../hooks/fast-jev.ts:38), 404). `sleep` зашит в код, поэтому ретраи
  нельзя проверить тестом.
- **Всё или ничего.** Сбой любого батча выбрасывает ответы всех предыдущих. Безопасная частичная
  стратегия есть: план, у которого ответили все шарды, применяется; неполный остаётся keep. Это
  не нарушает инвариант «MAX по всем шардам».
- `event.trigger` и `event.agentId` не учитываются. Toast'ы одинаковы для `manual`, `precompute`
  и компакции транскрипта субагента. `event.instructions` (текст после `/compact`) не
  используется как `goal`.

### Производительность
- **Квадратичный планировщик.** Для каждого кандидата `planBatches` → `makeBatchPlan` →
  `fitBatchStates` ([src/compact.ts:379](../src/compact.ts:379)). Тот для каждого исторического
  сообщения assistant пересобирает и сериализует всё состояние заново
  ([src/state.ts:515](../src/state.ts:515)). Шарды почти не зависят от батча (отличается только
  `evaluating`), поэтому их можно построить один раз, а вопросы упаковывать в них.
- Оценщик не калибруется. Jev возвращает `usage.input_tokens`, но это не используется.

### Безопасность и приватность
- Ключ в `settings.json` → `env` (§1). Резервное чтение ключа через `$.settings.read()`
  ([hooks/fast-jev.ts:330](../hooks/fast-jev.ts:330)) поощряет именно такую схему.
- В TypeSafe уходят весь пользовательский текст, входы инструментов (до 1000 символов) и превью
  результатов (2×1000 символов). Секреты из вывода (`cat .env`, токены в логах) никак не
  вычищаются, хотя для суждения о релевантности значение секрета не нужно.

### Смысл усечения
- Заметка `re-run the tool if needed` ([src/compact.ts:412](../src/compact.ts:412)) опасна для
  инструментов с побочным эффектом (`git commit`, `rm`, деплой). Модель повторит команду, чтобы
  «посмотреть вывод».
- `drop_result` оставляет только голову (300 символов). У сборок и тестов итог и ошибка обычно в
  хвосте.
- Пересобранное сообщение (без `handle`) движок строит из `text` и tool-блоков. Изображения и
  thinking в нём теряются, даже у результатов с решением keep. Последние 12 сообщений закреплены,
  поэтому риск низкий, но потеря молчаливая.

### Эксплуатация
- Умолчания заданы в трёх местах и расходятся: `plugin.json` (`minReductionRatio` 0), `HOOK_DEFAULTS`
  (0.25), `DEFAULT_OPTIONS`. Комментарии в [src/types.ts:121](../src/types.ts:121) устарели (25000,
  30000, «Default true in the local fork»). В описании `plugin.json` значится «durable diagnostics»,
  хотя диагностика удалена, а `diagnostic()` осталась пустышкой с десятком вызовов.
- Версия правится руками в четырёх местах, и никакой тест не проверяет, что они совпадают.
- Тестов на `register()` нет вообще: пути no-op, ошибки, малого сокращения и `turn.complete` не
  покрыты. Нет property-теста планировщика на случайных сессиях, а он поймал бы оба бага из §3.

## 5. RTK

**Встроить нельзя, и это не нужно.** RTK — фильтр на входе, только для Bash: он переписывает
команду и сам её исполняет с правилами для конкретной команды. fast-jev решает, что остаётся в
истории, и работает по всем инструментам. Это разные стадии одного бюджета контекста.

Данные за 2 недели (475 транскриптов, 23.7k результатов, 48M символов):

| Инструмент | Доля байтов результатов |
|---|---|
| Read | 44.1% — RTK сюда не достаёт, есть только Jev |
| Bash | 30.3% — в принципе территория RTK |
| graphiti-memory MCP | 14.2% |
| прочее | ~11% |

- Внутри Bash 68.5% байтов дают составные команды, начинающиеся с `cd …`. Для сравнения: за всё
  время `rtk gain` насчитал 657 команд, а Bash-вызовов только за 2 недели ~8.9k. Покрытие RTK
  на входе — отдельная задача вне этого репозитория: `rtk discover`, отучить агентов от префикса `cd`.
- Детерминированная дедупликация «по-RTK» почти ничего не даёт. Побайтно одинаковые повторы —
  0.2% всех байтов, у Read — 0.4%.
- Но **38.4% байтов Read — это ранние чтения файла, который потом читали ещё раз.** Удалять их
  детерминированно нельзя: содержимое менялось. Зато это сильная подсказка Jev: в вопрос о
  результате можно добавить `superseded_by: tN`.

**Что стоит взять у RTK:**
1. *tee*: неполный вид плюс указатель на полный оригинал. Заметка об усечении должна вести на
   `tool_use_id` в `.jsonl` транскрипта сессии (оригинал там остаётся), а не советовать
   «перезапусти». Усечение становится обратимым без побочных эффектов.
2. Усечение с учётом ошибок: голова **и** хвост.
3. *gain*: офлайн-скрипт по `compact_boundary` в транскриптах (сколько компакций, до и после,
   длительность, триггер). Плюс проверить, принимает ли движок `tokensBefore`/`tokensAfter` от хука
   (по типам — возможно). Если да, пропадает обманчивое «from 2.5k tokens».
4. *discover*: метрика «сожаления». Сколько раз после компакции модель заново вызвала тот же
   инструмент с тем же входом, чей результат был усечён. Это единственный эмпирический способ
   настроить `keepThreshold`, а не выбирать его на глаз.
