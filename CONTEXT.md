# Durable context — fast-jev-compaction-local

Обновлено: 27.09.2026.

## Идентичность

- Upstream: tamaratran/fast-jev-compaction 0.3.0.
- Local plugin: fast-jev-compaction-local@fast-jev-compaction-local.
- Upstream установлен отдельно и disabled.
- Текущий local release: 0.3.0-local.17.
- Единственный рабочий исходник: `C:\MCPs\fast-jev-compaction-local` (свой git с 22.09.2026;
  базовая точка — тег `v0.3.0-local.7`). Local marketplace указывает сюда.

## Зачем fork

Критерий изменён с «нужно ли хранить output verbatim / можно ли rerun» на информационную
релевантность корректному продолжению текущего разговора. Result question получает реальный
head/tail preview.

## Инварианты

- набранный владельцем текст не удаляется (вывод локальных команд — не он, см. local.15);
- урезанный или свёрнутый вызов и длинный вход любого старого вызова выгружаются на страницу
  (`<сессия, 8 символов>/<tool_use_id>.call.txt`, вход и результат), а не теряются; страница
  не перезаписывается;
- assistant text по умолчанию не удаляется: compactAssistantText=false;
- кандидаты по умолчанию — tool_use/tool_result;
- длинная история покрывается evidence shards;
- для target итоговый keep score = MAX по shards;
- Jev requests выполняются последовательно;
- с `handle` движку возвращается только текст пользователя; assistant и tool_result — всегда
  пересобранными (иначе движок пишет ссылки в несжатую историю, см. local.14);
- transport/429/5xx имеют retry (с учётом Retry-After, общий бюджет 150 s на компакцию),
  permanent errors — нет;
- **встроенное саммари Claude не запускается никогда.** Хук `session.compact` не вызывает
  `next(event)`: он отвечает сам — сжатыми сообщениями или `{ skip }`, в том числе при ошибке
  Jev, no-op и малом сокращении. Автокомпакция движка (это Claude summary) выключена
  `DISABLE_AUTO_COMPACT=1` в `~/.claude/settings.json` → `env`; автоматически сжимает только
  сам плагин из `turn.complete`. **Выключатель на случай, когда плагин не загрузился:**
  классический хук `PreCompact` в `~/.claude/settings.json` →
  `guard/block-builtin-compact.mjs` (код выхода 2). В 2.1.275 ядро запускает `PreCompact` в
  начале каждого своего пути (ручной `/compact`, реактивная автокомпакция, precompute) и при
  блокировке отвечает `{skip}` до запроса саммари. До ядра доходит только компакция, на которую
  не ответил Jev-хук, поэтому Jev выключатель не задевает. Проверено 22.09 безголовой сессией с
  выключенным плагином: `Compaction blocked by PreCompact hook: …`, 290 ms, 0 токенов. Увидел
  эту строку — значит, плагин не ответил, и её причину надо искать.

Planner рассчитан на два физических ограничения Jev: 64k total request и 32k state + longest
question. Поэтому большой разговор покрывается несколькими запросами, а не одним oversized state.

## Изменения local.17 (27.09): цель по замеру, компактные заглушки

**Живая проверка local.16** (сессия 28272b5c, `/compact` после `/reload-plugins`): последний
запрос до компакции 424.3k, первый после — **133.0k** (−69%). Движок записал `postTokens` 38.8k.
Состав 133k: сохранённые сообщения ≈33k (заглушки 103 свёрнутых вызовов 24k, полные вызовы 6k,
текст ассистента 2.3k, текст владельца 0.8k); всё остальное — не переписка: системный промпт и
схемы инструментов (~42k) и то, что движок кладёт обратно после компакции и с новой репликой —
список скилов (25k символов, после `/reload-plugins` дважды), CLAUDE.md (21k + 4.8k символов),
отложенные инструменты, инструкции MCP, @-файл первой реплики (20k символов). Плагин это не
видит и не трогает.

**Перелёт цели и холостой Jev.** Цель 15% = 150k, а вышло 133k: thinking оценён в 480 токенов на
блок (117 блоков = 56k), а в этой сессии было 82.4k (705 на блок; зависит от effort). Плагин
решил, что сообщений надо убрать на ~26k больше, очередь сворачивания исчерпалась — свёрнут
каждый старый вызов, где это выгодно (из полных старых остался один Edit на 671 символ).
Значит, оценки Jev в этой компакции **ни на что не повлияли**: 9 с и запросы впустую.

**Решение.**
- Цель считается от **измеренных** накладных расходов: после компакции плагин смотрит, сколько
  нёс первый запрос, вычитает свою оценку сохранённых сообщений и хранит остаток (`$.store`,
  ключ `after-compaction-overhead`, медиана 5 последних). Следующая цель для сообщений =
  `targetPercent·окно − накладные`. Пока замера нет, работает прежняя формула с thinking.
  Отчёт тогда предсказывает `накладные + сообщения после`.
- Первый запрос меряется на **первом вызове инструмента** хода (последний ответ тогда — ответ
  на первый запрос); `turn.complete` сосчитал бы в накладные все вызовы длинного хода. Прежний
  отчёт «first request after compaction carried N» этим и грешил.
- **Компактные заглушки.** Длинное поле свёрнутого вызова заменяется на `[N chars]`, если
  короткое поле уже говорит, что это было (`description`, `file_path`, `path`, `pattern`, `url`,
  `query`); иначе — первые 100 символов, как раньше. Голова вывода остаётся только у
  инструментов, чей вывод не лежит на диске (Bash, PowerShell, MCP…): у Read/Edit/Write/Grep/Glob
  это первая строка файла или «file updated». Замер на 103 заглушках: вход 21k символов, из них
  в опознающих полях 6.5k; голова вывода 10k, из них у Bash/MCP 7.9k. Моделирование на состоянии
  перед этой компакцией: −6.6k токенов.

Последствие для владельца: 15% теперь действительно ≈150k. Сегодняшние 133k — это ≈13%.

**Jev: что спрашивается и почему он сейчас не главный рычаг.** Вопрос на результат:
«содержит ли этот исторический результат информацию, ещё нужную для корректного продолжения»;
критерий «да» кончается фразой «неуверенность в том, чего нет в превью, — не довод за
нерелевантность». Jev видит всех пользовательских реплик дословно, свежий текст ассистента,
индексы, у вызова — вход, размер, превью головы и хвоста, «тот же объект вызван снова / файл
изменён позже», но **не тело**. То есть его спрашивают о содержимом, которого он не видит, и
велят при сомнении держать — отсюда 0.5–0.7 и AUC ~0.7 (local.15). В local.16 оценка только
упорядочивает (оценка / экономия); при разбросе оценок ×1.4 и экономии ×100 порядок почти
«крупное первым». Сколько сжать, решает цель, а не Jev.

Предложено владельцу, не сделано (меняет инвариант про неуверенность и требует прогона
оценщика по API): (1) не спрашивать Jev о вызовах, чей вывод лежит на диске, — сворачивать по
возрасту; (2) для остальных сменить вопрос с «можно ли удалить» на «держать в контексте или
хватит строки со страницей» и перевернуть правило неуверенности (чтение страницы дешёвое);
(3) показывать Jev тело крупных кандидатов вместо превью — вопросов станет в разы меньше, бюджет
запроса позволяет; (4) сравнить на 14 срезах с правилом без Jev.

## Изменения local.16 (27.09): сворачивание до цели, размеры в токенах Claude

Жалоба владельца после `/compact` на local.15: «saved 279.9k», хотя было 400k, а осталось 282k;
кто ошибается на 100k+; сжато всё ещё мало; прошлый контекст виден четыре раза. Разобрано по
сессии 94aba319 (4 границы, 5301 строка) и по коду движка 2.1.280 и Desktop 2.7032.

**Компакцию делал local.15**: страницы записаны 27.09 07:06, в сообщениях их пути. Перезагрузка
ни при чём.

**Кто ошибается.** Движок. Для компакции хуком `postTokens` = длина текста сообщений / 4 (функция
`Yd(e, 4)`), без системного промпта и схем инструментов (41.6k — это `cache_read` первого запроса
любой сессии). На токенизаторе Opus 5.5 этот контент стоит ~2 символа на токен, поэтому движок
занижает остаток почти вдвое, а «saved» = реальный `preTokens` минус эта оценка. Сверено на двух
компакциях с известным следующим запросом: 451k → движок 129k, факт 287.5k; 430.7k → движок 139k,
факт 316.7k. Desktop, кроме того, после компакции показывает в счётчике контекста `post_tokens`
границы до следующего ответа, отсюда «было 200k, сохранено 144k, осталось 150k». Хук эту цифру
изменить не может. Цифра плагина («меньше 282k») была близка к правде: по модели ниже остаток
≈271k.

**Оценщик размеров** ([src/size.ts](src/size.ts)): 2.03 символа на токен Claude. Калибровка —
422 пары соседних запросов четырёх сессий Opus 5.5 (рост входа минус вывод первого запроса =
ровно добавленные результаты): медианная ошибка 12% на результат, без перекоса кириллица/латиница
(1.02/1.00). Оценщик Jev для этого не годится: код и логи он считает в 1.3 раза ниже, кириллицу
в 1.5 раза выше. Thinking старого шага — ≈480 токенов на блок (440–530 на двух компакциях).
Проверка отчёта: «до − вырезанное − thinking» даёт 309k там, где следующий запрос нёс 316.7k
вместе с новой репликой.

**Почему мало.** После local.15 (моделирование `scripts/composition.ts` совпало с фактом:
385.6k символов против 384.6k) из ≈190k токенов сообщений: входы Bash 88k (46%) — скрипты в
heredoc, их никто не трогал; 270 результатов 70k — меньше ~1000 символов кандидатом не становится
никогда, а уже урезанная заглушка (300 + 300 + заметка ≈ 960 символов) остаётся навсегда;
выгруженные Write/Edit 24k; текст владельца и ассистента 5k. Сверх того системная часть 41.6k и
вложения ≈35k. Пол, до которого local.15 мог сжать, рос с каждым вызовом.

**Решение.**
- Длинные поля входа любого старого вызова (Bash, PowerShell, Agent…, не только Write/Edit)
  выгружаются детерминированно, с концами по `truncateHeadChars` и заметкой со страницей.
- Цель теперь достигается **сворачиванием**: старый вызов остаётся своим инструментом, поля
  входа по 100 символов, результат — заметка `paged out this <Tool> call (input and N chars of
  output): <страница>` и первые 100 символов вывода. Сворачивается любой старый вызов со
  страницей: мелкий, отложенный, урезанный прежней версией. Порядок — наименьшая нужность на
  сэкономленный символ: оценка Jev / экономия (прежде урезанный — 0.25, не оценённый — 0.5).
  Оценка Jev — это ещё и вероятность одного чтения страницы, так что это самый дешёвый в чтениях
  путь к цели.
- Страница одна на вызов: `~/.claude/fast-jev-pages/<первые 8 символов сессии>/<id>.call.txt`,
  вход и результат, как их первой увидела компакция. Уже существующая не перезаписывается
  (позже вызов виден уже сокращённым). Для заглушки прежней версии страница хранит её заметку,
  которая называет оригинал.
- Цель считается в токенах Claude: `before − targetPercent·окно − thinking − дубли/шум`.
- Отчёт: `context 400k → ≈150k tokens (−Mk of messages, ≈−Tk of N thinking block(s); the next
  reply shows the exact size. Claude Code's own "saved N tokens" line is …, not the size)`.

Моделирование на тех же состояниях (Jev заменён оценкой 0.6 всем, цель 15% от 1M): перед
компакцией 3 — ≈271k (local.15) → ≈150k; перед компакцией 2 — 316.7k (факт local.15) → ≈150k.
Сообщения 299k → 69k токенов, свёрнуто 207 из 267 старых вызовов, 77 входов выгружено.

**«Квадрирование» — в отображении и в файле, не в контексте.** Реальные запросы после компакций
совпадают с размером цепочки без дублей, `verify-transcript` чист. Но каждая компакция хуком
заново выводит всю переписку пересобранной под разделителем, и Desktop показывает её вместе с
прежней: копий на экране = компакций + 1 (после двух — «утроение», после трёх — «квадрирование»).
Кроме того, при компакции после переоткрытия движок дописывает в файл всю историю до предыдущей
границы с теми же uuid (строки 1903–2567 и 3397–4724 в 94aba319): файл растёт (16 МБ), контекст
нет. Обойти это хуком нельзя; с local.16 каждая повторная копия — это строки-записи, а не тела.

Не проверено вживую: безголовый `claude.exe` не авторизуется (истёк OAuth отдельного бинарника),
`live-compact.mjs` не запускался. Валидатор function hooks (`plugin validate`) модуль принял —
до правки он отверг `$.fs.list?.(dir)` как «использование `$` значением».

## Изменения local.15 (26.09): выгрузка вместо угадывания

**Почему upstream «работал», а форк нет.** Сверено с кодом upstream 0.3.0 из cache. Upstream
спрашивал Jev: «держать вывод дословно, только если содержимое ещё нужно **и повторный запуск не
заменит**». Результата Jev при этом не видел. Это смелое удаление, опирающееся на то, что всё
можно вернуть. Главное же: при ошибке Jev или сокращении меньше 25% upstream звал `next(event)`,
то есть встроенное саммари Claude, а его собственная автокомпакция из `turn.complete` не
срабатывала. На деле контекст сокращало встроенное саммари. Форк правильно запретил перезапуск
(у Bash и правок это повтор побочного эффекта) и саммари, но вместе с «можно вернуть» потерял
основание удалять: вопрос стал «содержит ли нужное», а на него Jev почти всегда отвечает «может
быть».

**Что измерено** (`scripts/evaluate.ts`, 14 срезов 7 реальных сессий, 715 кандидатов, живой Jev).
Прокси «нужно»: агент позже сам написал уникальное значение из урезаемой середины результата, не
прочитав его заново. Таких 103 из 715.
- Jev упорядочивает осмысленно (AUC 0.71), но калиброван плохо: оценки кучкуются в 0.5–0.7. Поэтому
  порог выбирает между «почти ничего» и «почти всё», и порогом это не лечится.
- Работа агента в состоянии Jev (журнал вызовов с превью) — AUC 0.72; вопрос «что потеряет
  удаление середины» — 0.63; вопрос upstream с заменой перезапуска на страницу — 0.58, Jev
  выгружает всё. Всё это отвергнуто.
- Где контекст: крупные результаты 29.5%, системная часть 21%, thinking 18.6%, **входы Write/Edit
  12.4%** (до local.15 их никто не трогал), вложения 8%, текст владельца и ассистента ~3%.

**Решение: урезание стало выгрузкой, а ручкой стала цель по размеру.**
- Страницы: полный текст каждого кандидата пишется в
  `~/.claude/fast-jev-pages/<session>/<tool_use_id>.txt` до решения Jev, и заметка об урезании
  называет файл (а если записать не удалось — транскрипт). Чтение страницы идёт без запроса
  разрешения (`tool.check`), и плагин считает эти чтения: «N page-in(s) since the last compaction»
  в итоговом уведомлении. Это прямая мера того, не выгружено ли слишком много.
- Входы Write/Edit/MultiEdit/NotebookEdit вне последних сообщений выгружаются детерминированно:
  длинные поля сохраняют концы, заметка называет `<id>.input.txt`. Потерь нет: файл на диске
  хранит актуальный текст, а после компакции хуком движок и так требует перечитать файл перед
  правкой.
- `targetPercent` (по умолчанию 15): компакция стремится довести контекст до этой доли окна.
  Сверх решений по порогу результаты выгружаются в порядке Jev, от наименее нужного, пока цель не
  достигнута; запись вызова остаётся. `0` — только порог, как в local.14.
- Старые выводы локальных команд (`<local-command-stdout|stderr|caveat>`, голые `/compact`,
  `/reload-plugins` и подобные) убираются вне последних сообщений. Это не текст владельца, а
  «Compaction blocked» часовой давности читался как вердикт только что сделанной компакции
  (26.09 06:00 → вопрос владельца в 06:52).
- Выключатель пишет каждую блокировку в `~/.claude/fast-jev-guard.log` (время, сессия, триггер),
  а в сообщении стоит время.

Живая проверка local.15 на четырёх крупных срезах (сокращение видимых сообщений, без thinking):
453k → меньше 274k, 568k → меньше 348k, 451k → меньше 264k, 240k → меньше 166k. Запись чистая
(`verify-transcript`). Цена: при цели 15% выгружаются почти все кандидаты, и по прокси агенту
потом понадобится 6–7 из них на компакцию, то есть 6–7 чтений страниц. Раньше это же при
урезании терялось.

Инвариант «текст пользователя не удаляется» уточнён: речь о набранном владельцем. Вывод
локальных команд им не является.

Не выяснено: почему `/compact` в 06:00 попал в выключатель. Хук в том же runtime отработал в
06:13 и 06:50; журнала runtime за 06:00 нет. С local.15 такой случай оставит запись в guard-логе.

Перед второй компакцией (06:50, после `/reload-plugins`) движок дописал в файл сессии копию всей
истории до первой границы, с теми же uuid (665 строк). В цепочку она не попадает, это рост файла,
а не контекста; источник — движок.

## Изменения local.14 (26.09): дубли, откат компакции, честные цифры

Жалоба владельца: «сохранено 144k», а осталось 150k; чат на 400k компакт не уменьшает; прошлый
контекст дублируется и даже утраивается. Разобрано по транскриптам 25–26.09 (сессии a7d30659,
ad1a9c0e) и по коду движка 2.1.280 — все три симптома подтверждены, причины такие.

**Дубли и откат — ошибка записи в движке, плагин её обходит.** Сообщение, которое хук вернул с
`handle`, движок пишет копией с новым uuid, но оставляет ей прежние `message.id` (у assistant) и
`sourceToolAssistantUUID` (у tool_result). Писатель ставит tool_result'у
`parentUuid = sourceToolAssistantUUID`, если такой uuid есть в файле, а он есть: это оригинал до
границы. При следующей загрузке сессии (Desktop переоткрыл чат, новый runtime) цепочка уходит через
такую ссылку в несжатую историю, а восстановление параллельных результатов (`NQr`) подтягивает все
записи файла с тем же `message.id`. Итог: компакция отменена, старые ходы дважды; после второй
компакции — трижды. В a7d30659 вторая компакция получила 190 пар в двух экземплярах (1.6M символов
против 0.86M), а при переоткрытии подтянулось бы 2021 лишняя запись.

Исправление ([src/transcript.ts](src/transcript.ts)): движку с `handle` возвращается **только текст
пользователя** (с ним остаются вложения, которые движок к нему приписал: CLAUDE.md, картинки
промпта). Каждое сообщение assistant и каждый tool_result пересобираются без `handle`: у них новый
синтетический id и линейный parent. Соседние строки одного ответа сливаются, за каждым вызовом идут
ровно его результаты. Результат, который движок дал только на `toolUses[].text`, становится
настоящим tool_result (в local.13 такой вызов после пересборки оставался без результата).

Что пересобранное сообщение не несёт, и чем это закрыто:
- thinking — движок и так выбрасывает его после любой компакции (`thinking_drop`, причина
  `prefix_mismatch`: в a7d30659 это 72 из 72 блоков и −46k токенов). Теперь это видно в отчёте;
- `tool_reference` из ToolSearch — в текст результата дописывается, какие инструменты были
  загружены и как загрузить их снова;
- вложения под строками инструментов, включая реплики, которые пользователь отправил посреди хода
  (`queued_command`). Их плагин записывает сам (`prompt.submit` с `turnId`, `$.store`, ключ
  `queued-prompts`) и на компакции возвращает текстом в тот tool_result, после которого они пришли.
  Реплики до local.14 не записаны, в уже повреждённых сессиях они теряются при первой компакции;
- картинки внутри результатов инструментов — теряются (результат остаётся текстом).

Уже повреждённая сессия лечится при первой компакции local.14: повторный `tool_use_id` и его
результат, а также дословно повторённый текст assistant в пределах хода убираются. Проверено вживую
на копии a7d30659 в состоянии 18:32: 95 дублей вызовов и 3 текста убраны, сообщения ~472k → ~231k.

**Ход ещё идёт** (последний вызов без результата) — компакция отказывается целиком: пересобранный
вызов без результата сломал бы продолжение.

**Цифры.** `preTokens` у границы — реальный размер запроса, а `postTokens` движок считает сам по
содержимому сообщений, без системного промпта, схем инструментов, вложений и thinking. Разность
выдаётся за «сэкономлено» и завышает эффект в разы (ad1a9c0e: «204k → 71k», фактически 200k →
164k). Хук эту цифру переопределить не может: для пересобранной компакции движок записывает свой
`postTokens`. Поэтому плагин пишет свою: `context Uk → under Ak tokens (−Ck of messages and N
thinking block(s) of unknown size …)`, где C — оценка `estimateTokens` по видимому содержимому
(калибровка на a7d30659: 275k против ожидаемых ~275–285k), а итог — верхняя граница: thinking
уходит тоже, но его размер плагину не виден. Точную цифру даёт следующий запрос. Если сессия была
переоткрыта с дублями, последний замер `usage` устарел; тогда отчёт — «messages ~X → ~Y».

**Почему Jev почти ничего не убирает.** Живой прогон на копии a7d30659 (378k): оценки результатов
Jev легли в полосу 0.52–0.70 («не знаю, скорее да»), ниже 0.5 — 6 из 55. Сокращение видимого
содержимого при разных `keepThreshold`, по живым прогонам Jev на той же копии:

| keepThreshold | урезано / удалено / оставлено | −токенов сообщений |
|---|---|---|
| 0.5 (профиль) | 6 / 0 / 49 | −9k |
| 0.6 | 27 / 4 / 24 | −44k |
| 0.65 | 37 / 6 / 12 | −97k |
| 0.7 | 40 / 9 / 6 | −149k |

К каждой строке добавляется ~46k thinking. Порог — решение владельца (профиль в `settings.json`).

**Загрузка плагина.** Headless 2.1.280 с `--setting-sources user` грузил хук прямо из
`C:\MCPs\fast-jev-compaction-local\hooks\hooks.json` (маркер local.14 до `plugin update`), хотя
`plugin list` показывал local.13. Какую копию берёт Desktop-runtime, по-прежнему смотреть по маркеру.

## Изменения local.13

- Claude Code может отдавать завершённый результат инструмента только внутри `SessionMessage.toolUses[].text`, без отдельного `toolResults`. Local.12 такие вызовы не считал парами и писал `nothing eligible (0 pinned tool pair(s))` даже в большой кодовой сессии.
- `collectToolCalls` теперь использует inline `toolUse.text` как fallback результата, когда отдельного `tool_result` нет. Незавершённый вызов по-прежнему игнорируется: у него нет ни explicit result, ни inline text.
- Размер transcript считает inline-result только если отдельного `tool_result` нет, поэтому reduction ratio не занижается и результат не откатывается как ложные 0%.
- No-op теперь выводит форму входа: сколько paired calls, raw `tool_use`, explicit `tool_result` и inline outcomes. Это отличает реальный «нечего сокращать» от очередного несовпадения API.
- Добавлены library- и hook-level тесты на inline-only outcome; полный suite перед выпуском: 65/65.

## Изменения local.12

- Уже сокращённый result считается сокращённым только по настоящей служебной заметке с тем же `tool_use_id` (или по legacy-формату), а не по любому вхождению строки `[fast-jev-compaction `. Это убирает ложные срабатывания на исходниках/чужих заметках и повторную оценку собственных новых truncation notes.
- `scripts/replay.ts --before-boundary` восстанавливает именно ветку от `compact_boundary.parentUuid`; поздняя sibling-ветка больше не подменяет историю в проверочном скрипте. Добавлен регрессионный тест.
- Release gate 22.09: typecheck зелёный; 62/62 unit tests зелёные; live synthetic fork сохранил весь диалог и без Claude summary сократил 25 626 → 1 705 символов (~93%). Проверка исходного рабочего transcript отдельно ограничена доступом клиента к `.claude`; обход защиты не используется.

## Изменения local.11

- Большой пользовательский текст и прежние саммари больше не блокируют планировщик: обе роли
  покрываются дословными частями. Огромное сообщение делится с указанием смещений. В выходной
  сессии пользовательский и assistant-текст не сокращается. Решение удалить по-прежнему требует
  низкого score во ВСЕХ evidence shards для этого target.
- Сначала проверяются самые объёмные результаты. Мягкий бюджет — 16 запросов за проход, только
  целые группы evidence shards; одна группа может превысить мягкий бюджет. Непроверенные
  кандидаты остаются целыми и отмечаются `deferred`. Внутри runtime следующий проход сначала
  проверяет ещё не оценённые tool_use_id; эта очередь не разрешает удаление по старому score.
- Уже усечённые результаты и мелкие выводы с минимальной возможной экономией не пересчитываются.
- Shell, изменения файлов и неизвестные MCP сохраняют запись действия; Jev может сократить их
  результат. Read/Grep и другие известные чтения допускают удаление пары по двум оценкам.
- Усечение сохраняет по 300 символов с каждого конца и tool_use_id для поиска оригинала в
  `.jsonl`; команда с побочным эффектом не предлагается к повторному запуску ради вывода.
- Общий deadline 150 s теперь обрывает и зависший HTTP-запрос; не запускает перекрывающийся
  повтор после таймаута. HTTP error body не попадает в лог; score вне [0,1] отвергается.
- Preflight использует тот же отбор кандидатов, что и compact; ручной compact запускает
  cooldown авто-компакции. `precompute` не выдаётся за уже применённое сокращение.

## Автокомпакция

`turn.complete` зовёт `$.session.compact()` (trigger `plugin`) **после** `await next(event)`:
движок отвергает вызов, пока ход не закрыт ядром («a turn is running … call it from
turn.complete or later»). До 0.3.0-local.8 вызов стоял до `next(event)` — по транскриптам с
20.09 не было ни одной компакции с trigger `plugin`/`auto`, все 11 — `manual`. Хук при вызове
из плагина пропускает только вызывающий хук (`turn.complete`), а `session.compact` того же
плагина событие видит, так что Jev-хук при этом работает.

Повтор не раньше, чем контекст вырастет на 10% окна от прошлой попытки: иначе контекст, который
Jev оставил выше порога, запускал бы компакцию на каждом ходу. Субагентские ходы автокомпакцию
не запускают. Отказ вызова показывается toast'ом один раз, дальше — в `ui.log`.

## Claude Code

Function hooks требуют >=2.1.274; при разработке проверена bundled 2.1.275 в Claude Desktop.
Отдельная PATH-версия (2.1.212) старее и не должна использоваться для диагностики Desktop hook.

После plugin update живой Code runtime держит старый versioned hook и после
`/reload-plugins` — проверено 22.09: `/reload-plugins` в 06:16:40Z, а `/compact` в 06:16:52Z
отработал ещё на local.7. Какую версию держит процесс, видно без догадок:
`~/.claude/plugins/cache/fast-jev-compaction-local/fast-jev-compaction-local/<версия>/.in_use/<pid>`
(в файле `procStartFt` — время старта процесса, FILETIME). Новая версия подхватывается только
новым Code runtime: переоткрыть Code-чат, весь Desktop не перезапускать. В toast — маркер
`fast-jev <LOCAL_BUILD> [trigger]`. `/reload-plugins` без `--force` не применяет изменения,
которые сбрасывают кэш промпта (так в коде движка), а для проверки версии он бесполезен.
Перед `/compact` его не делать.

## Проверенные наблюдения

Один ранний Jev run: 282234 -> 47887 примерно за 1.7 s, без isCompactSummary.

Длительность не означает, что сработал fallback. На разговоре в 229 сообщений со 106 парами
инструментов (реплей 22.09) Jev-компакция — это 6 последовательных запросов, 10–20 с. На 323
сообщениях со 156 парами local.8 делал 15 запросов и ~7 с планирования, это около минуты
(22.09 такую прервали на 56-й секунде). Local.10 на том же разговоре — 8 запросов и 0.1 с. До local.9
к ним добавлялись ~3.3 с синхронного планирования до первого запроса: планировщик был
квадратичным. 22.09 такую компакцию прервали на 15-й секунде, приняв её за встроенную.
Встроенное саммари на том же объёме — 40–120 с, и оно оставляет в транскрипте
`isCompactSummary` и boundary с `preservedSegment`. С local.9 Jev виден по ходу: toast
`fast-jev … Jev request k/N, t s` (не чаще раза в 3 с), итог — отдельным toast.

`preTokens`/`postTokens` в `compact_boundary` **не доказывают эффект**. До local.8 при ошибке
и no-op хук возвращал исходные сообщения, движок всё равно писал boundary (no-op 21.09:
`preTokens=2518`, `postTokens=61802`, 17 ms). Сессия 8c684e1d, 21.09 10:09 и 10:58: boundary
«541k → 219k» и «682k → 273k», а следующий запрос к API ушёл с 544k и 683k токенов — сжатие
не применилось. Причина подтверждена реплеем живой цепочки через планировщик: отказ
`all user messages plus the minimal global dialogue index exceed the Jev state limit (~79k
tokens, limit 30k)` за 71 ms (см. ниже).
Эффект проверять по `usage` первого ответа после компакции: с local.8 плагин сам показывает
toast «first request after compaction carried N tokens (before: M)».

До local.11 все сообщения роли user шли в каждый evidence shard целиком. Сюда попадали не только реплики
владельца, но и прежние саммари Claude и вывод slash-команд: в 8c684e1d это 88k + 17k символов
против 21k набранных. Оценщик токенов считает кириллицу по 0.9 токена на символ (английский
текст — примерно 0.21). Из-за этого state переполняется, и компакция длинной сессии отказывает
целиком. Решение — в плане методологии (`docs/review-2026-09-22.md`).

## Диагностика

Function-hook validator не разрешает произвольный node:fs import. Persistent file diagnostics
была удалена; использовать ui.log/toast и compact_boundary metadata, а для эффекта — `usage`
следующего ответа в `.jsonl` транскрипта.

`ui.log` и решения Jev по каждому вызову видны в `--debug-file` headless-запуска — на этом
построен `scripts/live-compact.mjs` (см. OPERATIONS.md). Целостность записанной компакции и то,
что загрузит переоткрытие, проверяет `scripts/verify-transcript.ts`.
