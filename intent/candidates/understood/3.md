# Исследование кандидата 3 — операционный контур и воспроизводимость

## Анализ

Запрос следует трактовать как **исправление существующего форка** `C:\MCPs\fast-jev-compaction-local`: неверные показатели при/после сжатия, старые реплики повторяются в Desktop, автоматическое сжатие самого плагина нужно выключить. Но условие «всё ещё» важно: перед поиском нового бага в алгоритме следует доказать, что пользователь видит **именно новую загруженную версию**, а не старую версию function hook в живом runtime или другой экземпляр upstream-плагина.

Первая гипотеза — **расхождение source / installed cache / active hook**. Исходники четырежды объявляют `0.3.0-local.19`; форк и upstream устанавливаются независимо. Однако после `plugin update` живой Code-runtime способен удерживать старый function hook даже после `/reload-plugins`. Внешне изменение в исходниках прошло успешно, а реальное поведение не меняется. Поэтому без проверки `LOCAL_BUILD` в toast новой сессии не считать ни исправление, ни регрессию доказанными.

Вторая гипотеза — **неоднозначный показатель**. Интерфейс содержит как минимум нативное сообщение Desktop «saved N tokens», приблизительный прогноз плагина и последующий toast на основании измерения реального запроса. Нативный `postTokens` не включает значительную часть накладных данных; исправление коэффициента пересчёта в `src/size.ts` не изменит его. Нужен эталон именно из `usage` первого ответа после `compact_boundary`, отдельно вычесть новый prompt, если требуется изолированная экономия. Не использовать количество токенов, написанное самой границей, как критерий успеха. Если пользователь жалуется исключительно на строку ядра, функциональный предел требует изменения Desktop/ядра или отдельного честного представления, а не косметической цифры форка.

Третья гипотеза — **повтор UI поверх корректной цепи**. Движок при `session.compact` сам добавляет пересобранные сообщения под новой границей, тогда как UI продолжает рисовать предыдущие сообщения. Изменение массива возвращаемых сообщений не способно стереть уже показанное из истории UI. После повторного открытия дополнительно возможны дубли в JSONL и лишние вложения `skill_listing`/инструкций; это уже надо измерять отдельно. Исправление ради UI не должно удалять оригинальный ввод владельца или его вложения и не должно портить active parent chain. Если проверка покажет, что UI-дубли порождены ядром, фиксировать ограничение на уровне плагина и задачу по клиенту, а не создавать опасную эвристику удаления.

Четвёртая гипотеза — **два независимых «auto»**. Штатное Claude summary уже запрещается внешним `DISABLE_AUTO_COMPACT=1` и `PreCompact` guard, но функция `turn.complete` в форке продолжает инициировать `$.session.compact()` при достижении порога. Отключение должно касаться второго механизма и не ломать обработчик ручного `/compact`. Бездействие при ошибке Jev — `{skip}`, а не `next(event)` с переходом на платное встроенное summary. Проверять не только опцию, но и фактическое число вызовов `session.compact()` после ответа модели.

## Доказательства

- `package.json:2-3`, `.claude-plugin/plugin.json:1-4`, `.claude-plugin/marketplace.json:6-12`, `hooks/fast-jev.ts:77`: исходный релиз в четырёх местах — `0.3.0-local.19`. Это **версия исходников**, не свидетельство о загруженном code runtime. `CONTEXT.md:468-480` и `OPERATIONS.md:71-95` документируют сохранение старого function hook в живой сессии и процедуру релиза.
- `OPERATIONS.md:161-179`: на реальных предыдущих сессиях зафиксированы расхождения `preTokens-postTokens` и фактического использования, а также дублирующийся UI-таймлайн. Там же описан воспроизводимый метод измерения через `cache_read_input_tokens + cache_creation_input_tokens + input_tokens` первой записи ответа после границы.
- `OPERATIONS.md:181-202`: существует `scripts/verify-transcript.ts` с кодом возврата и инвариантами `linksIntoHistory=0`, `sharedMessageIds=0`, `recoveredOnReload=0`, `chainStartsAfterBoundary=true`; это сильнее визуального теста одного скриншота.
- `hooks/README.md:7-20` и `hooks/fast-jev.ts:1006-1043`: прописан автоматический вызов после `turn.complete` (trigger `plugin`). `hooks/fast-jev.ts:745-749, 945-950` отдельно реализует Jev-only `session.compact` с безопасным `skip`.
- `CONTEXT.md:154-171, 282-288`: исторически находили одновременно ложные UI-повторы и реальные копии вложений; они различаются по последствиям. Доказательства относительно конкретной новой пользовательской сессии **ещё не собраны**, поэтому запрещён вывод «сейчас всё исправлено» или «сейчас точно повторно передаётся».

**Эксперименты** в нужном порядке: (1) без чтения значений секретов установить source-version, installed-version, active `LOCAL_BUILD`; проверять новый runtime, а не `/reload-plugins`; upstream остаётся disabled. (2) На копии обезличенной сессии использовать `scripts/verify-transcript.ts` и `scripts/composition.ts` для состояния до/после одной и двух компакций, отдельно построить счётчики UI-replay / JSONL / реальных токенов первого запроса. (3) Unit-тест порога 30%: фейковый `turn.complete` заканчивается ответом без `compact` и без HTTP к Jev, затем ручной `session.compact` сохраняет существующее корректное поведение. (4) Применить patch только после красного теста; выпустить новую patch-версию во всех четырёх местах, прогнать `npm run typecheck`, `npx vitest run`, `plugin validate`, проверить активный `LOCAL_BUILD` в **новом** runtime. Живые платные запросы и изменения `~/.claude/settings.json` не нужны для исходного доказательства.

## Вывод

Первый решающий шаг — **верифицировать активную версию плагина и собрать три независимых измерения**. Это исключит ошибочную правку исходников из-за устаревшего installed cache и не даст принять UI-регрессию за рост реального контекста. Для отключения автоматики достаточно менять источник вызова в `turn.complete`, сохраняя ручной Jev и отдельную блокировку штатного саммари. Ожидаемые инварианты после релиза: ручной `/compact` работает, автоматических вызовов Jev нет, токены считаются по реальному ответу после границы, переподключение сессии не создаёт неверных active parent-ссылок, текст и изображения владельца сохранены. Невозможность управлять нативной строкой «saved N» или старым UI-таймлайном должна быть зафиксирована явно, а не выдаваться за исправленный дефект форка.
